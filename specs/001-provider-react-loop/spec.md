# Feature Specification: Provider 抽象 + ReAct Loop（可调用工具的多轮对话）

**Feature Branch**: `001-provider-react-loop`

**Created**: 2026-07-29

**Status**: Draft

**Input**: User description: "Provider 抽象 + ReAct Loop : 让 OryxOS chat 能进行多轮对话，LLM 可决定调用工具（如查天气），OryxOS 执行后回填结果继续推理，直到给出最终回答。"

## Clarifications

### Session 2026-07-29

- Q: 工具调用的中间过程是否对用户可见？ → A: 可见——每次工具调用在终端输出一行式简要进度（工具名 + 执行状态/耗时），随后照常输出最终回答

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 多轮对话跑通（Priority: P1）

用户（开发者/运维人员）在终端启动 OryxOS 对话，与一个 Agent 进行多轮问答。
系统记住对话上下文，后续提问可以引用前文（如"那明天呢？"），直到用户主动退出。

**Why this priority**: 这是一切的地基——没有可用的对话链路，工具调用、记忆、
定时任务都无从谈起。只交付本 story 就是一个可用的 MVP（能聊天的 OryxOS）。

**Independent Test**: 启动对话命令，连续进行 3 轮以上有上下文依赖的问答，
验证每轮回答都能正确引用前文，即交付"可对话"价值。

**Acceptance Scenarios**:

1. **Given** 已配置好一个可用的模型提供商（密钥已通过环境变量提供），
   **When** 用户启动对话并发送第一条消息，**Then** 系统在可接受时间内返回该
   Agent 的回答。
2. **Given** 一个已进行中的对话（至少 1 轮历史），**When** 用户发送依赖上文的
   追问（如"那明天呢？"），**Then** 系统返回的回答体现出对前文的理解。
3. **Given** 用户启动对话时指定的 Agent 不存在或模型配置无效，**When** 命令执行，
   **Then** 系统给出明确的错误原因（而不是崩溃或静默失败）。
4. **Given** 对话进行中，**When** 用户发送退出指令，**Then** 会话正常结束，
   本次对话内容已留存。

---

### User Story 2 - LLM 自主调用工具完成任务（Priority: P2）

在同一对话中，用户提出需要外部数据才能回答的问题（如"北京今天天气怎么样，
适合穿什么？"）。模型判断需要调用工具，系统执行工具并把结果交还模型继续推理；
若模型再次请求调用工具则重复该过程，直到模型给出最终回答。用户看到的是一次
提问、过程中每次工具调用的一行式简要进度提示、以及一次最终回答，中间的
"思考→调工具→看结果→再思考"循环由系统自动完成。

**Why this priority**: 这是 OryxOS 区别于"裸聊天客户端"的核心价值——Agent 能
自主完成多步骤任务。依赖 US-1 的对话链路，但本身独立可测。

**Independent Test**: 准备至少一个可用工具（如天气/HTTP 查询类），提出一个必须
调用该工具才能回答的问题，验证系统在单次提问内完成"工具调用→结果回填→最终
回答"全过程，且最终回答包含工具返回的真实数据。

**Acceptance Scenarios**:

1. **Given** Agent 配置了至少一个可用工具，**When** 用户提出需要该工具才能回答的
   问题，**Then** 系统执行工具、回填结果，最终回答中包含工具获取的真实数据。
2. **Given** 一个需要多次工具调用的任务（如先查城市编码再查天气），**When** 用户
   一次性提出问题，**Then** 系统自动完成多轮"调用→回填"循环，中间无需用户介入。
3. **Given** 模型判断无需调用工具即可回答的问题，**When** 用户提问，**Then** 系统
   直接返回答案，不发生任何工具调用。
4. **Given** 工具执行失败（如目标服务不可达），**When** 失败发生，**Then** 对话
   不中断，系统把失败信息交还模型，由模型给出兜底回答或向用户说明情况。
5. **Given** 模型连续请求调用工具、循环达到系统上限，**When** 上限触发，**Then**
   系统终止循环，向用户返回已掌握的信息并明确说明"达到推理步数上限"，而不是
   无限循环或报错退出。
6. **Given** 一次提问触发了工具调用，**When** 循环进行中，**Then** 每次工具调用在
   终端显示一行式简要进度（工具名称 + 执行状态/耗时），循环结束后照常输出
   最终回答，进度提示不打断阅读流。

---

### User Story 3 - 模型提供商可配置、可切换（Priority: P3）

管理员通过配置为 Agent 指定使用哪家模型提供商、哪个模型；更换提供商只需修改
配置和对应的环境变量密钥，不改动任何代码。配置多家提供商时，每个 Agent 明确
绑定其中一家，不存在歧义。

**Why this priority**: "运行时切换无 lock-in"是 OryxOS 对企业的核心承诺之一，
但只要 US-1/US-2 跑通，系统已可用；多提供商并行是增强项。

**Independent Test**: 先后用两家不同提供商的配置启动对话，验证两轮对话都能正常
完成，且切换过程零代码改动。

**Acceptance Scenarios**:

1. **Given** 配置了提供商 A 的 Agent，**When** 改为配置提供商 B（模型、密钥环境
   变量同步更换）后重启对话，**Then** 对话功能表现一致，全程未修改代码。
2. **Given** 系统中同时配置了多家提供商，**When** 不同 Agent 分别绑定不同提供商，
   **Then** 各 Agent 的请求准确路由到各自绑定的提供商，互不串线。
3. **Given** 所需的环境变量密钥缺失，**When** 系统加载配置，**Then** 启动即给出
   明确的缺失提示，而不是在首次调用时才报错。
4. **Given** 提供商服务不可用或密钥无效，**When** 用户发送消息，**Then** 系统返回
   清晰的失败原因，且该次失败留有记录。

---

### Edge Cases

- 用户发送空消息或仅含空白字符：系统应提示重新输入，不发起模型调用。
- 单条消息超出系统允许的大小上限：系统应明确拒绝并告知限制，而不是截断后静默发送。
- 模型返回了格式无法解析的工具调用请求：系统应能容错（视为无效调用并反馈给模型
  纠正），而不是整个对话崩溃。
- 模型在一次响应中请求调用多个工具：系统应全部执行并一次性回填所有结果。
- 一次回答的整体耗时超过系统调用超时上限：系统应终止本次处理并告知用户，会话本身
  保持可用。
- 工具执行时间远超预期：工具调用受超时约束，超时按工具失败处理（走失败回填路径）。
- 对话进行中网络中断：当前轮次失败并给出提示，已产生的对话历史不丢失。

## Requirements *(mandatory)*

### Functional Requirements

**对话与会话**

- **FR-001**: 用户必须能通过命令行与指定 Agent 发起多轮对话，系统在会话期间维护
  完整的消息历史并将其作为上下文提供给模型。
- **FR-002**: 会话内容必须持久留存；进程重启后历史会话记录可查询（跨重启恢复会话
  上下文属于后续 Memory 能力，不在本特性范围）。
- **FR-003**: 系统必须拒绝空消息与超过大小上限的消息，并给出明确提示。

**推理循环（ReAct）**

- **FR-004**: 系统每次请求模型时，必须提供：Agent 的任务指令、会话历史、当前可用
  工具清单（名称、用途说明、参数格式）。
- **FR-005**: 当模型响应中包含一个或多个工具调用请求时，系统必须执行对应工具，
  将全部执行结果回填进对话上下文，并再次请求模型继续推理。
- **FR-006**: 当模型响应中不包含工具调用请求时，系统必须将该响应作为最终回答
  呈现给用户，并结束本轮处理。
- **FR-007**: "请求模型→执行工具→回填"的循环必须设有最大迭代上限（默认 10 次）；
  达到上限时系统必须终止循环，返回已掌握的信息并明确说明触发上限。
- **FR-008**: 工具执行失败或超时时，系统必须将失败信息（而非异常堆栈）回填给模型，
  由模型决定重试、换工具或向用户说明；对话不得因此中断。
- **FR-009**: 模型返回无法解析的工具调用请求时，系统必须将解析错误反馈给模型令其
  纠正，且计入迭代上限；系统自身不得崩溃。
- **FR-010**: 单轮处理（可能含多次迭代）必须有整体超时约束（默认 60 秒）；超时后
  终止本次处理并告知用户，会话保持可用。
- **FR-011**: 推理循环每次执行工具调用时，必须在终端输出一行式简要进度（至少包含
  工具名称与执行状态/耗时）；进度输出不得中断或延迟最终回答的呈现。

**Provider 抽象**

- **FR-012**: 系统必须支持通过配置为每个 Agent 指定模型提供商与模型；提供商密钥
  一律从环境变量读取，禁止以明文写入任何配置文件或代码。
- **FR-013**: 配置中引用的环境变量密钥缺失时，系统必须在加载配置阶段就报告缺失，
  而不是推迟到首次调用。
- **FR-014**: 同时配置多家提供商时，每个 Agent 的请求必须准确路由到其显式绑定的
  提供商，禁止出现路由歧义。
- **FR-015**: 更换提供商必须零代码改动——仅修改配置与环境变量即可生效。

**审计**

- **FR-016**: 每次模型调用都必须留存记录，至少包含：所属会话、提供商与模型、
  输入/输出内容或引用、token 用量、耗时、成功/失败、失败原因。
- **FR-017**: 每次工具调用都必须留存记录，至少包含：所属会话、工具名称、入参、
  结果或错误、耗时、成功/失败。
- **FR-018**: 审计记录必须持久保存，即使当轮对话失败也不得丢失已产生的记录。

### Key Entities *(include if feature involves data)*

- **会话（Session）**：一次持续对话的容器；包含所属 Agent、渠道来源、消息历史、
  创建/更新时间。
- **消息（Message）**：会话中的一条记录；角色可以是用户输入、模型回答、模型的
  工具调用请求、工具执行结果；按序排列构成对话上下文。
- **工具（Tool）**：系统向模型开放的能力单元；具有名称、用途说明与参数格式定义；
  本特性只消费 Tool 注册体系提供的工具，不定义具体工具实现。
- **Provider 配置**：Agent 与模型提供商的绑定关系；包含提供商名称、模型标识、
  密钥的环境变量引用（非密钥本身）。
- **调用记录（审计）**：一次模型调用或工具调用的留痕；关联会话，含耗时、成败与
  用量信息，只增不改。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 配置就绪后，用户从启动对话到收到首轮回答不超过 60 秒（模型服务
  正常的前提下）。
- **SC-002**: 需要 1 次工具调用的问题，用户在单次提问后 60 秒内收到包含工具真实
  数据的最终回答，全程无需任何中间操作。
- **SC-003**: 需要 3 次以内工具调用的多步任务，90% 以上能在一次提问内自主完成
  并给出最终回答，不触发迭代上限。
- **SC-004**: 达到迭代上限或工具失败的场景下，100% 的对话以"可读的回答或明确说明"
  结束，不出现崩溃、死循环或无响应。
- **SC-005**: 100% 的模型调用与工具调用留有持久审计记录，可核对每次调用的成败、
  耗时与用量。
- **SC-006**: 更换模型提供商的全过程（改配置 + 设环境变量 + 重启对话）不超过
  5 分钟，且不需要修改任何代码。

## Assumptions

- 本特性合并覆盖实施顺序中的 US-1（对接 LLM）与 US-2（ReAct 循环）两个 story，
  验收 Demo 为：对话中问天气类问题，系统自动调用工具并回答。
- 本特性只要求"工具可被发现、被调用、结果可回填"的机制闭环；9 个内置工具的完整
  交付属于后续 Tool 体系特性。本特性验收只需至少 1 个真实可用工具（如 HTTP 查询类）。
- 会话历史在会话期间全量保留作为上下文；上下文窗口的裁剪/压缩策略不在本特性
  范围（简单截断即可，记录为已知限制）。
- 跨重启恢复会话上下文、长期记忆属于后续 Memory 特性；本特性仅保证会话记录持久
  留存、可查询。
- 模型响应采用一次性返回（非流式）；流式输出为扩展阶段能力，不在本特性范围。
- 定时触发（cron）与 Web API 触发复用同一套推理循环，但这两个触发源本身的交付
  属于各自后续特性；本特性只验证命令行对话入口。
- 核心阶段运行环境假设为企业内网，本特性不涉及认证与多租户。
- 模型提供商的可用性、配额与网络连通性由使用者保障；系统只对失败给出清晰报错
  与留痕。
